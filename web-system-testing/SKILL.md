# Web System Testing Skill

## 核心职责

对网页系统进行高质量功能测试，输出符合标准化模板的中文测试报告。

## 简称定义

为避免歧义，明确以下简称：
- **manager** = project-manager（项目管理协调者）
- **tester** = project-tester（测试执行者）

## Prompt 传递要求（强制执行）

**【核心问题】Skill 被触发后，SKILL.md 只加载在 global 上下文中，manager 和 tester 是独立 agent，不会自动继承 skill 规则。**

因此，每次 Agent 调用时，**必须在 prompt 中明确传递以下关键内容**，不得假设被调用的 agent 已知道这些规则。

### 关键规则清单（所有 Agent 必须遵循）

以下规则是 Skill 的核心约束，**无论 prompt 中是否明确提到， tester 都必须默认遵循**：

| 规则类别 | 规则内容 | 来源 |
|----------|----------|------|
| **验证码处理** | 必须使用 `mcp__MiniMax__understand_image` 工具识别验证码，禁止使用OCR | Skill 固定规则 |
| **报告语言** | 所有内容必须使用中文，禁止英文 | Skill 固定规则 |
| **报告格式** | 四个 Sheet、详细测试结果14列（含用例ID列） | Skill 固定规则 |
| **截图命名** | `{用例ID}.png` 或 `{用例ID}_序号.png`（多张截图时），只保留Bug截图 | Skill 固定规则 |
| **用例执行** | 必须严格按照用例清单执行，不得随意增减 | Skill 固定规则 |
| **操作步骤真实性** | 操作步骤必须包含完整的数据操作（填写字段→保存→验证），禁止"点到为止" | Skill 固定规则 |
| **提交方式** | 完成后提交 manager 评审，不得直接告诉用户 | Skill 固定规则 |

**【重要】上表中来源为"Skill 固定规则"的，是 tester 默认必须遵循的规则，manager 无权取消或修改。**

### 传递给 manager 的内容（第一步调用时）

调用 project-manager 时，prompt 必须包含：
1. **测试目标**：用户要测试的系统、模块、轮次
2. **用户已确认的信息**：URL、账号、密码（如有）
3. **报告格式要求**：四个 Sheet、增删改查分行记录、全中文
4. **沟通记录要求**：必须记录所有 Agent 交互节点到 `team_communication_record.md`
5. **评审标准**：覆盖完整性、测试真实性、报告完整性、Bug准确性、语言一致性

### 传递给 tester 的内容（manager 调用 tester 时）

manager 调用 project-tester 时，prompt 必须包含：
1. **完整测试信息**：URL、账号、密码、模块、轮次、测试类型
2. **功能测试用例清单**（当选择 A 或 C 时）：用例ID、功能点、操作类型、优先级、操作步骤框架
3. **业务测试用例清单**（当选择 B 或 C 时）：用例ID、业务流程名称、操作步骤、预期结果
4. **操作步骤框架**：每个用例必须包含完整的操作步骤起点、过程、验证点

**【功能测试执行要求】**（当选择 A 或 C 时）
- tester 必须严格按照功能用例清单中的"操作步骤框架"执行，不得省略步骤
- 每个用例的操作步骤必须包含：**起点（点击哪里）→ 过程（填写/选择什么）→ 验证（期望什么结果）**
- **禁止"点到为止"**：不得仅点击按钮查看功能是否存在，必须执行完整的数据操作
- 新增：填写字段 → 保存 → 验证记录出现
- 查看：点击查看 → 验证具体数据显示
- 编辑：点击编辑 → 修改字段 → 保存 → 验证修改生效
- 删除：点击删除 → 确认删除 → 验证记录移除

**【业务测试执行要求】**（当选择 B 或 C 时）
- tester 必须严格按照业务用例清单执行
- 按用户描述的业务流程逐步执行，每步都需要截图记录

**【强制要求】**
- tester 必须严格按照用例清单执行测试，不得随意增减测试项
- tester 必须确保每个用例ID都有对应的测试记录
- tester 报告中的功能点和操作类型必须与用例清单一致
- **【关键】验证码处理必须使用 `mcp__MiniMax__understand_image` 工具，禁止使用OCR**

## 团队协作流程（强制执行）

```
用户 → [提出测试需求]
    ↓
【必须使用Agent工具调用project-manager】
    ↓
project-manager → [主动接管需求，协调团队]
    ↓
【必须使用Agent工具调用project-tester】
    ↓
project-tester → [执行测试]
    ↓
project-manager → [评审报告，不合格则返工]
    ↓
用户 → [接收最终结果]
```

**【强制执行】必须使用Agent工具启动团队协作：**

当收到测试需求后，**必须**按照以下步骤执行：

1. **第一步**：使用 `Agent` 工具调用 `project-manager` agent，协调团队执行测试
   - 在prompt中明确说明任务：测试目标、测试信息、输出要求
   - **重要**：调用后等待project-manager接管，manager将持续协调直到测试完成（包括返工）

2. **第二步**：project-manager使用 `Agent` 工具调用 `project-tester`
   - 分配测试任务（包含系统URL、账号、密码、模块、轮次）
   - tester执行测试

3. **第三步**：tester完成后提交manager评审
   - tester使用 `Agent` 工具发送报告给project-manager
   - **不得**直接向用户报告

4. **第四步**：manager评审后向用户报告最终结果

**【禁止行为】**
- 禁止以global身份直接执行测试，必须通过agent团队协作
- 禁止跳过project-manager直接让tester执行任务
- tester禁止直接向用户报告或询问

**Agent协作定义（强制明确执行顺序）**

| Agent | 类型 | 何时被调用 | 职责 | 输出 |
|-------|------|-----------|------|------|
| global | 协调启动者 | 用户提出测试需求时 | 调用project-manager，传递用户需求 | 等待manager完成 |
| project-manager | 管理协调者 | global调用后 | 接管需求、分配任务给tester、评审报告、返工决策、向用户交付、生成沟通记录 | 最终报告给用户、沟通记录 |
| project-tester | 执行者 | manager调用后 | 执行测试、生成报告、提交manager评审、记录沟通节点、**遵循Skill固定规则** | 报告给manager、沟通记录初稿 |

**关键规则**：
1. 用户只需提出需求，不需要参与测试过程
2. project-manager主动接管需求，协调团队分工
3. tester完成后**直接提交给manager评审**，不需要询问用户
4. tester**不直接对接用户**，所有沟通通过manager
5. 测试过程中除非**必须由用户确认的问题**（如环境、账号等），否则不允许断开会话
6. **【强制】每个Agent交互节点都必须记录到team_communication_record.md**
7. **【强制】tester 必须遵循 Skill 固定规则（见关键规则清单），无论 manager 是否在 prompt 中明确提到**

## 触发条件

当用户提到以下任一场景时，必须触发此技能：
- "测试xxx系统"、"自动化测试"、"功能测试"
- "测试报告"、"测试结果"、"生成报告"
- "测试增删改查"、"验证表单"
- 任何需要对网页系统进行验证并输出报告的场景

## 测试流程

### 阶段零：环境预检（强制执行，不得跳过）

**【目的】确保测试环境就绪，避免执行到一半才发现缺依赖。**

manager 在收到测试需求后，**必须首先执行环境预检**，检测以下依赖：

#### 预检依赖清单

| 依赖 | 检测方式 | 缺失时的处理 |
|------|----------|-------------|
| Python 版本 | `python --version` 要求 >= 3.7 | 提示用户升级 Python |
| playwright | `python -c "import playwright"` | 自动执行 `pip install playwright` |
| openpyxl | `python -c "import openpyxl"` | 自动执行 `pip install openpyxl` |
| Chromium 浏览器 | `python -m playwright install --check chromium` | 自动执行 `python -m playwright install chromium` |
| mcp__MiniMax__understand_image | 调用工具验证是否可用 | 提示用户配置 MiniMax MCP |
| Playwright MCP | 调用 `browser_navigate` 测试 |


#### 预检执行流程

```
1. 执行 Python 版本检测
2. 执行 playwright 包检测
   - 若缺失，自动安装：pip install playwright
3. 执行 openpyxl 包检测
   - 若缺失，自动安装：pip install openpyxl
4. 执行 Chromium 浏览器检测
   - 若缺失，自动安装：python -m playwright install chromium
5. 验证 mcp__MiniMax__understand_image 工具可用性
   - 若不可用，提示用户配置 MiniMax MCP
6. 验证 Playwright MCP 工具可用性
   - 调用 browser_navigate 尝试打开空白页
   - 若 Playwright MCP 不可用，提示用户检查 Playwright MCP 配置

【重要】环境预检时不需要检测 Chrome DevTools MCP，避免两者同时启动导致冲突。Chrome DevTools MCP 只在测试执行阶段 Playwright MCP 降级时才使用。
```

预检完成后，向用户展示结果：

✅ Playwright MCP 可用

【环境状态】：就绪，可以开始测试
【浏览器策略】：测试执行阶段优先使用 Playwright MCP，导航失败时自动切换 Chrome DevTools MCP
```

**【强制要求】**
- 环境预检必须先于所有步骤执行
- 缺失的依赖必须自动安装，不得跳过
- 预检结果必须向用户展示
- 只有预检全部通过后才能进入阶段一
- **【重要】环境预检时只检测 Playwright MCP，不检测 Chrome DevTools MCP，避免两者同时启动导致冲突**

### 阶段一：信息收集（强制执行，不得跳过）

**【强制要求】测试前必须向用户确认以下信息，未确认不得开始测试：**

| 信息项 | 说明 | 示例 | 是否必填 |
|--------|------|------|----------|
| 系统URL | 完整的登录地址 | http://www.land-info.cn:38084/sc-forest | 必填 |
| 登录账号 | 用户名 | admin | 必填 |
| 登录密码 | 密码 | scadmin% | 必填 |
| 测试模块 | 要测试的具体模块 | 采伐证核发 | 必填 |
| 测试轮次 | 第X轮测试 | 第十二轮 | 必填 |

**执行步骤：**

1. 向用户发送确认信息，格式如下：
```
【测试信息确认】
在开始测试前，请确认以下信息：
- 系统URL：？
- 登录账号：？
- 登录密码：？
- 测试模块：？
- 测试轮次：第几轮？

2. **等待用户回复**，收到确认信息后才可以进入阶段二
3. 如果用户提供了部分信息，缺少的部分必须询问，不得假设
4. 不得查看历史测试记录来推断当前测试的信息

**【测试类型确认】**

在基础信息确认后，询问用户测试类型：
```
【测试类型确认】
请确认您需要的测试类型：

A. 功能测试 - 验证系统的增删改查、详情查看等标准功能是否正常
B. 业务测试 - 验证您自定义的业务流程（如：新增数据→前往某模块→执行查询→验证结果）

```

- 如用户选择 **A（仅功能测试）**：使用标准增删改查用例
- 如用户选择 **B（仅业务测试）**：记录业务流程描述，制定业务测试用例，不执行标准功能测试
- 如用户选择 **C（两者都要）**：同时制定功能测试用例和业务测试用例

**【业务流程与注意事项询问】**（仅当用户选择 B 或 C 时）

当用户选择 B 或 C 时，**必须**进一步询问：
```
【业务流程与注意事项】

请描述您的业务流程（如需多个业务测试，请分别描述）：
格式示例：模块A → 操作1 → 模块B → 操作2 → 验证结果

示例：
1. 动物声纹库-新增声纹→声纹监测-查看列表→筛选该设备→验证数据存在
2. 设备管理-新增设备→声纹监测-查看设备→验证设备显示

测试过程中是否有需要注意的地方？（如：某字段有特殊校验规则、某些操作需要额外等待等）
```

**【测试数据规范】**（测试执行时必须遵循）

当测试涉及需要填写身份证号码时，必须使用符合国家标准的有效身份证号码：

**18位身份证号码结构**：
| 位置 | 含义 | 说明 |
|------|------|------|
| 第1-6位 | 地址码 | 省、市、区代码 |
| 第7-14位 | 出生日期码 | 格式YYYYMMDD |
| 第15-17位 | 顺序码 | 第17位区分性别（奇数男/偶数女） |
| 第18位 | 校验码 | 根据前17位加权计算得出 |

**校验码计算方法**：
1. 将前17位号码与加权因子相乘并求和
   - 加权因子：7, 9, 10, 5, 8, 4, 2, 1, 6, 3, 7, 9, 10, 5, 8, 4, 2
2. 总和除以11取余
3. 余数匹配校验码表：0→1, 1→0, 2→X, 3→9, 4→8, 5→7, 6→6, 7→5, 8→4, 9→3, 10→2

**示例**（地址码510101，出生日期19900101，顺序码123）：
```
加权和 = 5×7 + 1×9 + 0×10 + 1×5 + 0×8 + 1×4 + 1×2 + 9×1 + 9×6 + 9×3 + 0×7 + 0×9 + 1×10 + 0×5 + 1×8 + 2×4 + 3×2 = 189
余数 = 189 ÷ 11 = 17 余 2
校验码 = X（对应余数2）
正确身份证号：51010119900101123X
```

**【强制要求】**
- 测试数据必须使用符合规范的格式
- 不得使用随意生成的数字组合作为测试数据
- 如不确定测试数据的正确格式，应询问用户或查阅相关规范

**【禁止行为】**
- 不得查看历史测试报告来推断当前测试信息
- 不得使用上一轮测试的URL、账号、密码（除非用户明确指定）
- 不得在未收到用户确认前开始测试

### 阶段二：用例制定（强制执行，不得跳过）

**【目的】确保测试覆盖完整、报告与用例一致，防止漏测。**

manager 在分配任务给 tester 前，**必须**完成以下步骤：

**【用例制定策略】**（根据阶段一用户选择的测试类型执行）

| 用户选择 | 执行内容 |
|----------|----------|
| A（仅功能测试） | 制定标准增删改查用例（见 2.1-2.3） |
| B（仅业务测试） | 制定业务测试用例（见 2.4），跳过 2.1-2.3 |
| C（两者都要） | 先制定标准用例（见 2.1-2.3），再制定业务用例（见 2.4） |

#### 2.1 访问系统，制定用例清单

1. **访问被测系统**：使用 webapp-testing 技能登录系统
2. **梳理功能结构**：列出模块下所有功能点
3. **确定操作类型**：每个功能点必须覆盖 新增/查看/编辑/删除/详情展示 五种操作
   - **新增**：新建记录并保存
   - **查看**：查看列表记录
   - **编辑**：修改已有记录
   - **删除**：删除已有记录
   - **详情展示**：进入详情页面，验证详情内容（适用于有点击进入详情功能的列表页面）
4. **制定用例清单**：按以下格式输出

```
用例清单格式：
| 用例ID | 功能点 | 操作类型 | 优先级 | 操作步骤框架（制定时明确） |
|--------|--------|----------|--------|---------------------------|
| TC-001 | 一般林木申请 | 新增 | P0 | 点击"新增申请"按钮 → 填写申请人、联系电话、采伐类型等字段 → 点击"提交申请" → 验证提交成功提示 |
| TC-002 | 一般林木申请 | 查看 | P0 | 点击列表中某记录的"查看"按钮 → 验证详情弹窗显示完整表单信息 |
| TC-003 | 一般林木申请 | 编辑 | P0 | 点击列表中某记录的"编辑"按钮 → 修改联系电话字段 → 点击"保存" → 验证修改生效 |
| TC-004 | 一般林木申请 | 删除 | P0 | 点击列表中某记录的"删除"按钮 → 在确认弹窗中点击"确定" → 验证记录移除 |

```

**计算示例：**

| 场景 | 功能点数 | 操作类型 | 详情子Tab数 | 应测用例数 |
|------|---------|----------|-------------|-----------|

**判定规则：**
- 如果某功能点只有3条用例 → **不合格**（缺少1条）
- 如果某功能点只有查看没有其他 → **不合格**

#### 3.0 浏览器工具容错策略（强制执行）

**【目的】确保在 Playwright MCP 无法正常导航时能够继续执行测试。**

| 工具 | 优先级 | 适用场景 |
|------|--------|----------|
| Playwright MCP | 优先使用 | 常规操作（点击、填表、选择、下拉菜单等） |
| Chrome DevTools MCP | 降级使用 | Playwright MCP 导航失灵、操作超时、元素定位失败时 |

**降级判定条件（满足以下所有条件才切换）：**
1. 同一操作连续 **3 次**失败
2. 且确认不是元素定位错误（如：元素存在但点击无效）
3. 且同一用例尝试切换不同定位方式后仍失败

**【放宽说明】**
- 不要因为偶尔1-2次失败就切换工具，系统偶发抖动是正常的
- 优先尝试更换元素定位方式（用 text、title 等替代 uid）
- 只有当同一操作反复失败（如点击某个按钮3次都不成功），才考虑降级
- 降级前应先尝试 Chrome DevTools MCP 作为备选定位方式

**降级执行流程：**
```
1. Playwright MCP 操作失败
2. 先尝试更换定位方式（如：用 text 替代 uid）重试
3. 如更换定位方式后成功，继续使用 Playwright MCP
4. 如连续3次同一操作失败，记录详细错误信息
5. 切换到 Chrome DevTools MCP 重试
6. 如仍失败，标记该用例为"阻塞"，记录错误，继续下一个用例
```

**【必须记录的降级错误信息】**
降级时必须在备注列记录以下信息：
```
Playwright MCP 降级，原因：{具体操作，如"点击新增按钮失败"}
错误详情：{工具返回的具体错误信息}
尝试解决：{尝试过的解决方法，如"更换定位方式仍失败"}
最终工具：Chrome DevTools MCP
```

#### 5.1 读取用例清单

#### 5.3 评审决策

| 情况 | 决策 |
|------|------|
| **格式校验任一项不合格** | **直接不通过**，列出不合格项，安排返工（格式问题优先级最高） |
| 报告条数 < 用例条数 | **不通过**，列出遗漏项，安排返工 |
| 存在未测试的操作类型 | **不通过**，明确指出哪个功能缺少哪种操作 |
| 存在"点到为止"的虚假操作 | **不通过**，列出哪个用例ID的哪种操作存在虚假测试，安排返工 |
| 存在数据一致性问题 | **不通过**，列出哪个用例ID存在哪些一致性问题，安排返工 |
| 报告条数 = 用例条数 且 覆盖完整 且 操作步骤真实 且 数据一致 且 格式校验全部通过 | **通过** |

**【数据一致性评审细则】**

为防止报告中各列数据矛盾、虚假数据等问题，manager评审时必须检查以下一致性：

| 检查项 | 异常判定标准 | 处理方式 |
|--------|-------------|---------|

| | 操作类型为"删除"，但步骤中无删除确认、验证记录移除的信息 | 判定为**不合格**，要求返工 |
| | 操作类型为"编辑"，但步骤中无修改字段、验证修改生效的信息 | 判定为**不合格**，要求返工 |
| | 操作类型为"查看"，但步骤中无验证数据显示的信息 | 判定为**不合格**，要求返工 |
| | 操作类型为"详情展示"，但步骤中无点击进入详情、验证详情内容的信息 | 判定为**不合格**，要求返工 |
| **性能测试异常值检测** | 多个用例的性能测试值完全相同（如全是"1000ms"） | 判定为**可疑数据**，要求 tester 说明测量方式或提供原始数据 |

| **测试结果与实际结果一致性** | 测试结果为"通过"但实际结果描述了错误/失败 | 判定为**不合格**，要求返工 |

## 完整测试流程示例

```
用户：我要测试采伐证核发模块

manager：好的，我来协调团队执行。

【阶段一：信息确认】
manager：测试前请确认以下信息：
  - 系统URL：？
  - 登录账号：？
  - 登录密码：？
  - 测试模块：？
  - 测试轮次：第几轮？

用户：URL是xxx，账号admin，密码xxx，测试采伐证核发模块，第一轮

manager：收到，开始执行测试。

【阶段二：用例制定】
manager：先访问系统，制定用例清单。
  ↓ manager 登录系统，梳理功能结构
  ↓ 制定用例清单（如：一般林木申请[新增/查看/编辑/删除]、待审核[查看/编辑]...）
  ↓ 统计应测总条数：XX 条
  ↓ 将用例清单传递给 tester

【阶段三：测试执行】
  ↓ tester 按用例清单执行测试
  ↓ tester 使用 Playwright MCP 执行测试
  ↓ 如遇导航失败，自动切换 Chrome DevTools MCP
  ↓ tester 记录工具切换情况到备注列
  ↓ tester 报告给 manager：测试完成，请评审

【阶段四：报告生成】
  ↓ tester 提交报告给 manager

【阶段五：评审与返工】
manager：对比用例清单与报告...
  - 用例总条数：XX 条
  - 报告总条数：YY 条
  - 遗漏用例：[列出遗漏项]
  ↓ 评审结果：XX（通过/不通过）
  
（如果评审不通过）
manager：报告不合格，需要返工。
  ↓ 直接安排 tester 返工
  ↓ tester 返工完成，再次提交 manager 评审
  ↓ （重复直到通过）

（评审通过）
manager 报告给用户：第一轮测试完成，报告在xxx位置，通过率xxx%
```
